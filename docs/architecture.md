# Архітектура Backend Core

## Оновлення 28.10.2026

Додано PostgreSQL 16, Prisma 7 із adapter-pg, початкову модель User та міграцію,
Docker Compose app/db, `/api/v1/health`, OpenAPI JSON і Swagger UI. Див. [актуальний звіт](trello-tasks.md).
User не має публічного API, auth/RBAC не реалізовано. Один Prisma pool створюється на server lifecycle,
перевіряється до listen і закривається після HTTP drain. За відсутності DATABASE_URL дозволено HTTP-only режим.
Бізнес-сховище решти CRM та audit storage ще не реалізовані.

## Реалізовано

Один процес: HTTP server → request context → Helmet → CORS → JSON parser → `/api` routers → 404 → error handler.
Liveness endpoints: `GET /api/health` і `GET /api/v1/health`; документація — `/api/docs/` та `/api/openapi.json`. Він перевіряє лише живий процес.
Конфігурація перевіряється до відкриття порту. Application factory дозволяє ізольоване тестування.
Помилки 400/403/404/409/413/415 мають стандартний envelope; несподівані помилки — безпечний 500 без stack/message винятку.
Після початку відповіді JSON-помилку вже не можна надіслати: з’єднання закривається,
а лог містить лише requestId та RESPONSE_ABORTED, без оригінального винятку.
Express environment явно береться з перевіреної конфігурації.
AppError призначено лише для свідомо публічних 4xx повідомлень. Логи містять метадані, не payload.
При SIGINT/SIGTERM listener закривається, поточним запитам дається обмежений час на завершення.

## Передбачено, але не реалізовано

Modular monolith: спільний deployment, явні модульні межі. Вебкабінет і Chrome Extension
користуються одним API та однаковими правилами дублів, доступів і пауз. Окремої БД extension немає.
Не створено порожніх каталогів для майбутніх модулів та демонстраційних сховищ.

| Частина | Майбутня відповідальність |
| --- | --- |
| Authentication / Authorization | Ідентичність, ролі, перевірка прав на кожному захищеному запиті та ресурсі |
| Банки і люди | Банки, групи, підрозділи, сталі люди, зайнятість, контакти, знайомства |
| Відносини і напрями | Мета, стан, відповідальний, учасники, наступна дія; паралельні напрями |
| Задачі і команда | Строки, результати, передача відповідальності та задач |
| Історія | Події листів/дзвінків/зустрічей з людиною, банком, розмовою, напрямом, джерелом |
| Кампанії | Послідовності, стани учасників, паузи, спільні виключення, захист від повторів |
| Пошук контактів | Пошук/перевірка email, актуальність, сигнали зміни роботи |
| Міграція | Monday/експорти, зіставлення полів, дублі, повний звіт |
| Звіти | Покриття, актуальність, прострочені дії, стан інтеграцій |
| AI | Резюме з джерелами й датою, пошук, чернетки; підтвердження менеджером |
| Основне сховище / audit | Дані, файли листів, хто/що/коли змінив, резервні копії |
| Background jobs | Довгі операції, стани, повтори без дублювання |
| Integration Gateway | Адаптери провайдерів, sync status, помилки, reconciliation, matching replies |
| Технічний кеш | Лише прискорення, не джерело контактів або рішень про відправку |

Gateway отримує події нового листа, відповіді, недоставки і передає їх модулям історії та кампаній.
Майбутні workers викликають ту саму бізнес-логіку; провайдери не викликаються напряму з контролерів.
PostgreSQL і Prisma додано за новим завданням; рішення щодо черги та кешу залишаються майбутніми.

## Інваріанти майбутніх модулів

**Контакти.** Людина зберігає ідентичність при зміні роботодавця. Попереднє місце роботи закривається
датою, нове відкривається; старий робочий email не вважається актуальним. Email має статус перевірки.
Надійні нормалізовані ідентифікатори (email/LinkedIn) використовуються для дублів. Одночасне додавання
має захищатися транзакційно/обмеженнями сховища; нечіткі збіги й суперечливі дані йдуть на ручний розбір.
Два менеджери можуть бути учасниками одного запису; конфлікт відповідального потребує рішення.
Extension показує існуючий запис і зміни, записує тільки після підтвердження менеджером.

**Доступи.** Менеджер, керівник, адміністратор. Перевірка прав на кожному захищеному запиті,
включно з доступом до конкретних банків, людей і дій. Публічної реєстрації немає; перший адміністратор
створюється захищеним bootstrap-механізмом. Передача відносин і задач зберігає історію й аудит;
за відсутності прав потрібен запит керівнику.

**Паузи.** Кожна має охоплення, причину, автора, час. Змістовна відповідь ставить контакт на паузу до
обробки менеджером і охоплює учасників тієї самої розмови; не зупиняє інший напрям автоматично.
Пауза всього банку — тільки явне рішення з причиною й відповідальним. Заборона контактувати діє
в усіх каналах і кампаніях. OOO не ставить паузу. Bounce запускає перевірку email, не паузу відповіді.
Перед реальною відправкою обмеження перевіряються повторно за основним сховищем; вже поставлені
в чергу повідомлення теж зупиняються. Семантику «розмова або напрям» потрібно уточнити, не розширювати мовчки.

**Інтеграції.** Недоступний провайдер не блокує збереження людини без email: статус «не перевірено».
Фонові операції мають явні стани очікування/помилки і безпечні повтори. Невідомий результат відправки
спочатку звіряється з провайдером; сліпий retry заборонений. Повторна доставка подій не дублює історію.
Невідомий відправник — ручний розбір. Відповідь створює задачу менеджеру. Зміна роботи — задача
відновити контакт. Імпорт зберігає конфлікти й незіставлені поля у звіті, не губить їх.
AI не відправляє повідомлення і не змінює факти самостійно.

## Потребує погодження

- Остаточний framework / TypeScript; зараз свідомо Express + JS.
- Модель доступів, межі команд/організацій, auth transport, безпечний bootstrap адміністратора.
- Транзакції та стратегія дублів/ручного злиття; PostgreSQL/Prisma вже налаштовано.
- Gmail чи Outlook, email provider, можливості та обмеження LinkedIn.
- Семантика розмов/напрямів, каналів і відновлення кампаній після паузи.
- Строки зберігання даних, audit, backup/restore, production deployment та observability.
- Підтвердження запропонованих блоків першого релізу та формату Monday export.

Довідка щодо технічних рішень: [Node.js releases](https://github.com/nodejs/node/releases),
[Express 5 error handling](https://expressjs.com/en/5x/guide/error-handling/).
